Comparison methodology: mae vs dino vs polarmae

How the four-row metric table in mae/docs/v3_final_comparison.md was produced for each of the three SSL pipelines. Each section names the runs, scripts, and outputs that generated the numbers.

1. Shared task setup

Every probe in the comparison evaluates the same pixel-level 3-class task (track / shower / other) on the same dataset slice. Only the feature source (the trained backbone) varies per architecture.

Probe independence (no weight sharing)

Every probe is freshly initialized and trained from scratch. No weights are shared, in any direction:

  • Within one architecture, the four probes (sft_feat, sft_raw, voxel_svm_feat, voxel_svm_raw) are four separate classifiers with their own weights. The MLP heads do not share with each other, the SVMs do not share with each other, and the MLPs do not share with the SVMs.
  • Across architectures, mae's MLP, dino's MLP, and polarmae's MLP are three separately-instantiated heads — each trained only on its own backbone's features.
  • Across mae's SSL epochs, a fresh DensePixelHead is constructed at every epoch boundary — no carry-over from one epoch's probe to the next. (This is why mae's per-epoch trajectory is a noisy line, not a monotonically-improving curve.)
  • The only thing the four probes share, within a single architecture's evaluation, is the probe pool itself (5000/class × 3 = 15 k voxels). All four probes read from the same pool so that the four numbers describe four orthogonal cuts through the same data, not four different sample draws.

Concretely, in the code:

# mae   - mae/scripts/train_mae.py:_fit_dense_head
torch.manual_seed(seed)
head = DensePixelHead(in_ch=X.shape[1], n_classes=n_classes).to(device)   # new every call

# dino  - dino/diagnostics/run_probes.py:_fit_dense_head
torch.manual_seed(seed)
head = DensePixelHead(in_ch=X.shape[1], n_classes=n_classes).to(device)   # new every call

# polarmae - polarmae/eval/probes.py:_train_head
head = _SmallHead(X.shape[1], n_classes).to(device)                       # new every call

Likewise LinearSVC(...) is instantiated fresh in every SVM call across all three pipelines.

Scripts written for this evaluation

  • dino/diagnostics/run_probes.py — new. For a given checkpoint, loads dino's student + teacher backbones, builds a streaming per-class pool of 5000 voxels/class (capped on the fly to keep memory bounded), applies the FeatureLogTransform(3.75, 83861.2) normalizer that dino was trained with, then runs the same four probes on both the student and the teacher feature.
  • gridutils/probe_dino.sh — Condor worker. Loops over a list of checkpoints in one allocation.
  • gridutils/submit_probe_dino.sh — submitter. Defaults to the three checkpoints above.

Where the numbers come from

Three JSONs, one per checkpoint: probes_checkpoint_epoch10.json, probes_checkpoint_epoch50.json, probes_checkpoint_epoch100.json. Each has two views (student, teacher), each with the four probe blocks (sft_feat / sft_raw / voxel_svm_feat / voxel_svm_raw) — same schema as one entry of mae's sft_history.json.

Implementation notes

  1. State-dict format mismatch. dino was trained when attn_default in BACKBONE_REGISTRY resolved to MinkUNetSparseAttentionCore. The registry has since been refactored to wrap the core in a dense input/output adapter (MinkUNetSparseAttention), so checkpoint keys (conv0.0.weight, …) no longer match the wrapper's keys (core.conv0.0.weight, …). The loader sniffs the first key and loads directly into the Core class when the prefix is absent.
  2. Streaming pool. A naive "collect-everything-then-pool" approach hit a 32 GB OOM (~60 GB needed per view at 80k images × ~3k voxels × 64-d float32). We rewrote the pool builder to drain the loader, classify pixels per-image, and append to the per-class pool only while it has room. Peak memory ~ 10 MB regardless of dataset size; per checkpoint runs in < 1 min once classes saturate.

That launches the PyTorch-Lightning trainer. The APA2DProbeCallback is attached in the config and runs every N steps, writing probes_step{N}.json into the probes/ subdirectory.

How polarmae turns per-patch tokens into per-voxel features

vit_small produces 256 patch tokens of dim 384. The probe needs a feature per voxel, so _extract_per_voxel_features() performs an inverse-distance K-NN upsample from the FPS centers: 

K = min(5, T)                                              # K=5 nearest tokens
dists, idx, _ = knn_points(xyz_pts, centers, K=K)          # voxel -> nearest FPS centers
weight = 1.0 / (dists + eps)
weight = weight / weight.sum(dim=2, keepdim=True)          # normalised softmax-of-distance
voxel_feats = (gathered_tokens * weight).sum(dim=2)        # (B, N, 384) per voxel

So each voxel's 384-d feature is the inverse-distance weighted average of the 5 nearest patch-token embeddings. The probe MLP / SVM then sees (N voxels, 384) — same interface as the mae and dino paths.

Where the numbers come from

probes/probes_step{N}.json — the "best" column in the comparison table is the max val_macro_f1 across all step snapshots for each probe.

6. Caveats / non-equivalences across pipelines

The probes are byte-identical between mae and dino (they share DensePixelHead, the same LinearSVC call, the same _collect_*_pool semantics). They are not byte-identical to polarmae's implementation:

  • Different raw-feature scaling. mae and dino use (channel_int, tick_int, log1p(charge)); polarmae uses ((ch - 525)/600, (tick - 562)/600, 0, log_charge_in_[-1,+1]). Same information content (the constant 0 channel is degenerate), but different scales ⇒ different SVM / MLP convergence.
  • Different probe MLP head. mae/dino: DensePixelHead — 3-layer (in → 128 → 128 → 3), BN + ReLU, plain CE. polarmae: _SmallHead — 2-layer (in → 128 → 3), GELU, inverse-frequency class-weighted CE.
  • Different image splits. mae/dino use torch.randperm(seed=0) on the 100k-truth dataset for train / val. polarmae uses two explicit dataset paths (probe_data_path, probe_val_data_path) which may not coincide with mae's split.
  • Different per-class pool composition. Within each cap of 5000, the specific voxels depend on iteration order, which differs across pipelines (different batch size, different sampler).

Net effect: the raw rows (sft_raw, voxel_svm_raw) span ~0.06 absolute across pipelines (0.43-0.53). This spread is preprocessing noise, not a property of the architectures. The meaningful per-pipeline signal is the gap sft_feat − sft_raw — what the backbone is buying you on top of raw position+charge.

# 3. polarmae (from the PoLAr-MAE repo; trains + probes; ~few hours)

After all three complete, parse the relevant JSONs (see Section 7) and fill in the table. mae's sft_history.json is the canonical schema; dino's per-checkpoint JSON and polarmae's per-step JSON both contain one entry of that schema (plus a views wrapper for dino's student / teacher).
