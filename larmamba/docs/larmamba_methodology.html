larmamba: a linear-time (Mamba/SSM) foundation model for 2D LArTPC data

DUNE APA wire-plane pixel data (channel × tick, sparse). Branch may15. Runs in uvenv-polar-mae (torch 2.5.1+cu124), imports PoLAr-MAE. Date 2026-06-13.

1. Goal & idea

Earlier work established that on this DUNE pixel-PID task (3 classes: track / shower / other), PoLAr-MAE (FPS+ball-query tokenizer → ViT self-attention transformer → Chamfer reconstruction) reached ~0.93–0.94 feature-probe macro-F1, while sparse-CNN MAE/DINO models plateaued at ~0.65–0.72. The gap was architectural — tokenization + a global sequence mixer.

PoLAr-MAE's global mixer is self-attention, which is O(T²) in token count T. larmamba asks: can we keep polarmae's accuracy but make the encoder O(T) by swapping self-attention for a bidirectional Mamba (selective state-space) mixer? Target: ≥0.90 macro-F1 at lower / better-scaling cost. Cost metric of interest: peak GPU memory (performance prioritised).

2. Architecture — what changed, what was reused

Reused from PoLAr-MAE verbatim (the parts that earned 0.93): the FPS+ball-query tokenizer, the APA2D dataset, the Chamfer+energy reconstruction loss, the LightningCLI training loop, and the 4-probe APA2DProbeCallback evaluation. larmamba runs in polarmae's env and imports it directly.

Replaced: only the encoder's sequence mixer. larmamba.MambaEncoder is a drop-in for polarmae.layers.encoder.TransformerEncoder — same prepare_tokens / transformer / embed_dim interface that the loss and probes rely on — but its transformer is a stack of MambaBlocks instead of attention Blocks. The config simply points model.encoder.class_path at larmamba.MambaEncoder; the decoder stays attention (training-only, doesn't affect inference).

2.1 The three larmamba-specific pieces

PieceFileWhat / why
Serializationlarmamba/serialize.py Mamba is a 1-D recurrence, but point tokens have no natural order. Tokens are ordered along a Morton/Z-order space-filling curve over their (channel,tick) centers so neighbours in the scan are spatial neighbours (PointMamba / Point-Cloud-Mamba recipe). Invalid/masked tokens sort to the tail.
Bidirectional Mamba mixerlarmamba/mamba_block.py BiMambaMixer + MambaBlock: in-proj → depthwise conv → selective SSM scanned both directions (Vim-style) → gate → out-proj, in a residual block reusing polarmae's MaskedLayerNorm / MaskedDropPath / Mlp. Masked tokens are made transparent (Δ=0 ⇒ state passes through untouched).
Selective scanlarmamba/ssm.py The core h_t = a_t h_{t-1} + b_t recurrence. Two backends: (a) the official mamba-ssm CUDA kernel (fast, memory-optimal) on GPU; (b) a pure-PyTorch chunked + gradient-checkpointed parallel scan as CPU / fallback. Unit-tested: parallel vs sequential reference agree to ~1e-6 on both forward and gradient.

2.2 Engineering notes worth keeping

  • Centers seam: transformer(x, pos, mask) carries no geometry, so MambaEncoder.prepare_tokens stashes the token centers on the transformer for the serialization step.
  • Kernel install: no PyPI/torch-2.10 wheels exist, but the training env is torch 2.5.1+cu124, for which mamba-ssm 2.2.5 + causal-conv1d 1.5.0.post8 cu12 wheels do. Installed additively into uvenv-polar-mae (polarmae never imports them → baseline untouched); the package __init__'s transformers dependency is bypassed by importing the ops submodule directly.
  • dtype: under bf16-mixed autocast the kernel requires u/delta/B/C to share one dtype; they're unified to u.dtype in the wrapper.
  • Memory: the pure-torch scan first OOM'd in autograd (it stored O(log T) full (B,T,E,N) tensors). Rewritten to a chunked + checkpointed scan with persistent memory O(B·T·(E+N)). The kernel sidesteps this entirely.

All three ran the full 20k steps; the values cluster within ~0.005 (probe-pool noise). More tokens do not improve accuracy — 256 groups already capture event structure for this task. Recommended operating point: 256 tokens.

PoLAr-MAE's tokenizer uses coverage-based CNMS grouping, so on real sparse data the realized token count is bounded by num_init_groups and by event coverage; the sweep varies the cap, not a hard token count. Training peak memory (~40–45 GB for all three) is dominated by the attention decoder + the probe SVM extraction, not the Mamba encoder — so it does not separate token counts. The clean encoder cost is in §5.

  • Latency: Mamba ~linear (32× tokens → ~38× time); attention ~quadratic (16× tokens → ~200× time). Mamba is 3× faster at 1024, 9× at 4096.
  • Memory: Mamba linear (1.8 GB at 8192); attention OOMs at 8192. At 4096 Mamba uses ~16× less memory.
  • At T=256 (the saturating point) they are comparable — attention is even slightly faster. Mamba's advantage is scaling headroom, not the current operating point.

End-to-end encoder benchmark (with the tokenizer): Mamba ~2.6× faster than attention at equal tokens; there, peak memory is dominated by the shared FPS/CNMS tokenizer (~20 GB), not the mixer.

6. Conclusions

  • Quality goal met: larmamba is a PoLAr-MAE-quality 2D-LArTPC foundation model. Using a Mamba mixer instead of self-attention costs ~nothing in accuracy.
  • This task doesn't need the scaling (256 tokens saturate) — so the immediate payoff is "same accuracy, comparable cost at 256 tokens, with a much cheaper tail."
  • The linear encoder is decisive for regimes attention can't reach: finer tokenization, 3D / multi-plane / full-APA inputs, or longer sequences (8192+ tokens at <2 GB where attention OOMs).
  • CPU-portable: the unit-tested pure-PyTorch scan fallback runs without the CUDA kernel.

# train (1×L40S, ~2-3 h with the mamba-ssm kernel)
bash gridutils/submit_larmamba.sh larmamba_full  larmamba/configs/larmamba_apa2d_full.yml
bash gridutils/submit_larmamba.sh larmamba_g512  larmamba/configs/larmamba_apa2d_g512.yml
bash gridutils/submit_larmamba.sh larmamba_g1024 larmamba/configs/larmamba_apa2d_g1024.yml

8. Open follow-ups

  1. Distill / shrink the encoder (fewer layers, smaller d_model) now that 256 tokens suffice — push inference cost lower at the current operating point.
  2. Exploit scaling: finer tokenization or 3D/multi-plane inputs where attention can't fit — test whether larmamba exceeds polarmae.
  3. Replace the attention decoder with Mamba (training-only memory).
  4. Multi-GPU / longer pretraining (current: single-L40S, 20k steps).
